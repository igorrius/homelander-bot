# M1 Web Screens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The M1 screens of the React app — resident page, registration, login and the whole admin panel — working against the JSON API of plan 2.

**Architecture:** One React app in `web/`. Typed API calls live in `web/src/api/` (DTO types, one TanStack Query hook or mutation per endpoint); pages live in `web/src/pages/` and `web/src/pages/admin/`, one file per screen; small shared pieces (per-locale text picking, error translation, per-locale inputs, the built-in houses illustration) live in `web/src/lib/` and `web/src/components/`. Tests mock `fetch` with a tiny route table, so every screen is tested through the real `api()` client and the real hooks.

**Tech Stack:** React 19, TypeScript 7, Vite 8, Mantine 9 (`@mantine/core`, `@mantine/hooks`, new: `@mantine/notifications`), react-router 8, react-i18next 18, TanStack Query 5, new: `qrcode.react` 4 (renders an inline SVG, allowed by the CSP); Vitest 5 + Testing Library + jsdom; oxlint.

**Spec:** `docs/superpowers/specs/2026-11-27-m0-m1-foundation-and-identity-design.md` (sections 5.4, 5.5, 5.6, 5.7). The API is plan 2's Tasks 11–12 (`docs/superpowers/plans/2026-11-27-m1-backend-and-bot.md`), implemented in `internal/httpapi/public.go`, `admin.go`, `dto.go`, `errors.go`. Builds on M0 Task 5 (`docs/superpowers/plans/2026-11-27-m0-foundation.md`).

## Global Constraints

- Every user-facing string is a key in **both** `web/src/locales/uk.json` and `web/src/locales/en.json` (`locales.test.ts` enforces equal key sets). No Ukrainian or English literals in `.tsx` outside tests. Ukrainian is the default locale.
- The API returns codes only; the web translates them: `errors.<code>` for top-level codes (`validation`, `bad_request`, `not_found`, `conflict`, `forbidden`, `last_admin`, `rate_limited`, `try_later`, `invalid_code`, `unauthorized`, `internal`, plus `unknown` for anything else) and `validation.<reason>` for field reasons (`required`, `invalid`, `too_long`, `out_of_range`, `taken`, `linked`, `has_residents`, `type`, `size`). An unknown code or reason shows `errors.unknown` / `validation.invalid`, never the raw code.
- Admin-entered texts are `LocalizedText = Partial<Record<Locale, string>>` and are edited with one input per supported locale.
- Shown per-locale text = value for the current UI language, else for the site's `defaultLocale`, else the first non-empty value, else a translated fallback.
- No real addresses, phone numbers or community names in code, tests or fixtures. Test phones `+380500000001`…`+380500000099`; houses "House A", "House B"; community "Test Community".
- All API calls go through `api<T>()` from `web/src/api/client.ts` (adds `/api/v1`, `X-Requested-With: homelander`, same-origin cookies).
- Mutating buttons are disabled while their request is in flight.
- `cd web && npm run lint && npm run typecheck && npm test && npm run build` and root `make lint && make test` stay green after every task.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. One PR into `main`, merged after PR #29 (`feat/m1-backend`, this branch's base).

## Review Focus

1. The session ends while an admin works (expired, revoked, logged out in another tab) → the next admin request answers 401 and the app sends them to `/login`, not to an error loop or a blank page (Task 5 test `redirects to login when a request answers 401`).
2. On `/register`, picking an apartment and then changing the house → the apartment is cleared and its options come from the new house's range; a number outside the new range is never submitted (Task 4 test `clears the apartment when the house changes`).
3. Site texts filled in only one locale, viewed in the other → the default-locale text is shown, and with no text at all a generic greeting; never an empty header (Task 1 test `localized falls back…`, Task 2 test `falls back to the default-locale community name`).
4. A double click on "Send code", "Log in" or "Submit application" → exactly one request (Task 3 test `sends one code request on double click`).
5. An API answer with a code the web does not know (a 500 `internal`, a future code) → the translated generic error, never the raw code (Task 1 test `errorText of an unknown code is the generic text`).
